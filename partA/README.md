А.1 — Муу API-ийн алдааны шинжилгээ

`bad API` болох `usr_mgr` классыг харахад API дизайны хэд хэдэн зарчмыг зөрчсөн байсан.

1. Нэршил ойлгомжгүй, стандарт зөрчсөн

class usr_mgr { ... }
public db_conn: any;
public users_arr: Array<any>;
do_user_op(...)
get_u(...)

-Нэршлүүдийг харахад яг юу хийдэг нь шууд ойлгогдохгүй байна. Жишээ нь get_u гэдэг нь user буцаах уу, өөр зүйл хийх үү гэдгийг нэрнээс нь таахад төвөгтэй.

-Мөн usr_mgr, db_conn гэх мэт snake_case ашигласан нь TypeScript дээр түгээмэл биш. Ер нь кодыг дараа нь уншихад ийм жижиг зүйлс нэлээн их нөлөөлдөг юм шиг санагдсан.

-Иймээс нэршлийг аль болох ойлгомжтой, нэг хэвийн байлгах нь дээр гэж бодсон. UserManager, getUser, dbConnection гэх мэт бол шууд уншаад ойлгогдоно.

2. Дотоод өгөгдөл шууд ил гарсан

public db_conn: any;
public users_arr: Array<any> = [];

-Энэ хэсэг дээр class өөрийн өгөгдлөө хамгаалахгүй байна. Гаднаас хэн ч шууд өөрчилж чадна:

usr_mgr.users_arr.push(...)

-Ийм үед class өөрийн state-ийг хянах боломжгүй болно. Энэ нь encapsulation алдагдаж байгаа классик жишээ юм шиг санагдсан.

-Ийм зүйлээс зайлсхийхийн тулд private болгож, шаардлагатай үед getter ашиглах нь илүү зөв.

3. Нэг метод дотор олон үйлдэл чихсэн байна

do_user_op(obj, flag: number, timeout)

-flag-аас хамаараад create, update, delete, restore хийдэг. Гэхдээ flag = 2 гэвэл яг юу хийж байгааг шууд ойлгохгүй.

-Энэ нь өмнөх нэршлийн асуудалтай бас холбоотой — код уншихад байнга “энэ юу билээ” гэж бодогдуулахаар байна.

-Ер нь нэг метод = нэг үүрэг байх нь илүү ойлгомжтой байдаг. Тиймээс үйлдлүүдийг тус тусад нь салгах нь логиктой:

createUser(...)
updateUser(...)
deleteUser(...)

4. any төрлийг хэт их ашигласан

db_conn: any
users_arr: Array<any>
do_user_op(obj: any, ...)

-Эндээс харахад TypeScript ашиглаж байгаа утга бараг алга. obj яг ямар бүтэцтэй байх ёстой нь тодорхойгүй.

-Практикт ийм код ашиглахад алдаа их гарах магадлалтай. Жишээ нь буруу field дамжуулсан ч compiler барихгүй.

-Иймээс User, CreateUserDto, UpdateUserDto гэх мэт тодорхой type-ууд ашиглах нь илүү найдвартай санагдсан.

5. Алдааг string-ээр буцааж байна

get_u(): string
// 'ERR_404'

-Энэ нь хамгийн их анзаарагдсан асуудлуудын нэг. Зарим үед user буцаана, зарим үед 'ERR_404' string буцаана.

-кодыг if (res === 'ERR_404') ... гэж шалгах хэрэгтэй болно. Энэ нь нэлээн эмзэг харагдсан.

-Үүнийг засахдаа exception ашиглах нь илүү тохиромжтой юм шиг. Нэг хэвийн error handling-тэй болно.

6. JSON string буцааж байна

get_u() нь user-ийг JSON string болгож буцааж байна. Энэ нь жаахан илүүц санагдсан.

-Хэрэглэгч бүр parse хийх шаардлагатай ба service layer serialization хийж байна

-Үүнийг засахдаа User объектыг шууд буцаах нь зөв болов уу гэж бодсон. JSON болгох ажил нь controller талд нь байх ёстой.

7. Database-ийн алдаа шууд гадагш гарч байна

throws SQLException

-UserManager ашиглаж байгаа код database-ийн талаар мэдэх ёсгүй. Гэтэл SQLException шууд гарч ирж байна.

- Хэрэв дараа нь DB-ээ соливол API хэрэглэгчдэд нөлөөлөх эрсдэлтэй.

-Иймээс дотоод алдааг барьж аваад өөрийн domain-д тохирсон error болгох нь илүү зөв санагдсан:

UserNotFoundError
UserRepositoryError

8. Нэг параметрт хоёр өөр утга холисон

get_u(id_or_email: string, flag: number)

-Энэ нь бас жаахан төвөгтэй санагдсан. flag-аас хамаараад ID-аар эсвэл email-аар хайна.

-Гэхдээ энэ нь өмнөх 3-р цэгтэй адил — нэг метод дотор олон логик оруулсан асуудал.

-Мөн API ашиглаж байгаа хүн заавал “flag хэд билээ” гэж санах хэрэгтэй болно. Энэ хоёр нь тусдаа үйлдэл:

getUserById(...)
getUserByEmail(...) ингэж салгавал илүү ойлгомжтой болно

9. Хайлтын API тодорхой биш

find(q: string)

-q гэдэг нь яг юу вэ гэдэг нь ойлгомжгүй. Нэр үү, email үү, эсвэл бүгдээр нь хайж байна уу гэж бодох хэрэгтэй болно. Ийм API-г ашиглахад documentation харах шаардлагатай болдог.

-Ингэхийн оронд хайлтын нөхцлийг объект болгож өгвөл илүү ойлгомжтой:

searchUsers(criteria) - ингэснээр ямар талбараар хайж байгааг шууд харж болно.

10. timeout параметр ойлгомжгүй

timeout: number

Ямар нэгж вэ гэдэг нь тодорхойгүй (ms уу, сек үү?). Мөн метод бүр дээр дамжуулж байгаа нь бага зэрэг давтагдсан санагдсан.

Үүнийг constructor дээр төвлөрүүлэх нь илүү цэгцтэй юм шиг санагдсан:

class UserManager {
  constructor(private timeoutMs: number) {}
}
