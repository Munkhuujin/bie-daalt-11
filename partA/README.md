# А хэсэг — API дизайн ба сан

## А.1 — Муу API-гийн алдааны шинжилгээ

Доорх `usr_mgr` класс (`partA/src/bad/usr_mgr.ts`) нь API дизайны олон зарчмыг зөрчсөн байна. Доор **8 гол алдааг** тодорхойлж, аль зарчмыг зөрчсөн, хэрхэн засах талаар тайлбарлав.

---

### Алдаа №1: `public db_conn: any` — дотоод DB холболт ил гарсан

**Зөрчсөн зарчим:** Мэдээллийн далдлалт (encapsulation)

**Тайлбар:** Өгөгдлийн сангийн холболт бол дотоод хэрэгжилтийн нарийн ширийн зүйл. Үүнийг `public` байдлаар гадагш гаргаснаар гадны код `usr_mgr.db_conn = null` гэх мэт санамсаргүй өөрчлөлт хийх эрсдэлтэй. Мөн дараа нь өгөгдлийн сангийн номын санг солих шаардлага гарвал бүх call site-ыг шалгах шаардлагатай болно.

**Засвар:** `private` болгож, зөвхөн дотор ашиглана. Эсвэл dependency injection-ээр constructor-т нь өгнө.

---

### Алдаа №2: `public users_arr: Array<any>` — дотоод өгөгдлийн бүтэц ил

**Зөрчсөн зарчим:** Мэдээллийн далдлалт + төрлийн аюулгүй байдал

**Тайлбар:** Дотоод `users_arr` массивыг гадна код шууд `push`, `splice` хийж өөрчилж чадна. Энэ нь бизнес дүрмийг (жишээ нь давхар email зөвшөөрөхгүй) тойрон гарах боломж олгоно. Мөн `Array<any>` нь ямар төрлийн өгөгдөл хадгалж байгааг ойлгуулахгүй.

**Засвар:** `private users: Map<UserId, User>` болгож, зөвхөн метод (createUser, findById гэх мэт) ашиглан хандах.

---

### Алдаа №3: Тоон флаг (`flag: 0=create, 1=update, 2=delete, 3=restore`)

**Зөрчсөн зарчим:** Ойлголтын жин (cognitive load)

**Тайлбар:** `do_user_op(x, 2, 1000)` гэсэн дуудалтыг харахад `2` юу гэсэн утгатай вэ гэдгийг ойлгохын тулд comment-ийг уншиж, санаж байх шаардлагатай. Энэ нь код уншихад хүнд, алдаа гаргахад амархан болгоно. Жишээ нь 2 ба 3-ыг андуурч, устгах ёстой хүнийг сэргээх зэрэг.

**Засвар:** Нэг үйлдлийн флаг биш, тусдаа метод хэрэглэх: `createUser()`, `updateUser()`, `deleteUser()`, `restoreUser()`.

---

### Алдаа №4: `do_user_op` — нэршил ерөнхий, юу хийхийг илэрхийлэхгүй

**Зөрчсөн зарчим:** Нэршил (naming)

**Тайлбар:** Функцийн нэр нь юу хийх нь тодорхой байх ёстой. "do_user_op" гэсэн нэр "хэрэглэгчид ямар нэг үйлдэл хийх" гэсэн хэт ерөнхий утгатай — юу хийх нь флагаас хамаарна. Энэ нь функцийг шалгах, тестлэх, ойлгоход хүндрэл учруулна.

**Засвар:** Үйлдлийг нэр болгон оноох: `createUser`, `updateUser` гэх мэт.

---

### Алдаа №5: `obj: any`, буцах `any` — төрлийн аюулгүй байдал алдагдсан

**Зөрчсөн зарчим:** Төрлийн аюулгүй байдал (type safety)

**Тайлбар:** `any` төрөл нь TypeScript-ийн шалгалтыг тойрсон "escape hatch". Энэ нь caller ямар ч бүтэцтэй объект өгч, ямар ч утга буцааж авч чадна. Үр дүнд нь алдаа run-time хүртэл илрэхгүй.

**Засвар:** Тодорхой interface ашиглах: `CreateUserInput`, `UpdateUserInput`, `User` гэх мэт.

---

### Алдаа №6: `get_u(id_or_email)` — нэг аргумент хоёр төрлийн утга авах

**Зөрчсөн зарчим:** Нэг функц = нэг үүрэг (single responsibility)

**Тайлбар:** Функц нь оролтоор `id` эсвэл `email` авах боловч "аль нь байна" гэдгийг дотроо таамаглана. Энэ нь caller-д зориулсан API-г ойлгомжгүй болгох бөгөөд дотор нь `if/else` logic хэрэгтэй болгоно. Жишээ нь "user123" гэсэн string — энэ id юу, email үү?

**Засвар:** 2 тусдаа метод: `findById(id: UserId)` ба `findByEmail(email: Email)`.

---

### Алдаа №7: Алдааг string хэлбэрээр буцаах (`'ERR_404'`)

**Зөрчсөн зарчим:** Алдааны зөв илэрхийлэл (error handling)

**Тайлбар:** Олдохгүй үед JSON string биш `'ERR_404'` буцаадаг. Caller заавал `if (result === 'ERR_404')` гэж шалгах ёстой. Хэрэв бичгийн алдаа гаргаж `'ERR404'` гэж харьцуулбал алдаа мэдэгдэхгүй. Мөн буцах төрөл нь `string` ч, зарим үед JSON, зарим үед код байна — энэ нь төрлийн гэрээг эвддэг.

**Засвар:** Олдохгүй үед `null` буцах (find үйлдлийн хувьд) эсвэл `UserNotFoundError` exception шидэх (update/delete үед).

---

### Алдаа №8: `find()` нь `SQLException` шидэх — абстракцийн алдагдал

**Зөрчсөн зарчим:** Давхарга хоорондын абстракц (layer abstraction)

**Тайлбар:** `usr_mgr` нь өгөгдлийн сантай ажилладаг гэдгийг гадна давхарга мэдэх ёсгүй. SQL exception-ийг шууд нэвтрүүлэх нь:
1. UI давхарга SQL-ийн талаар мэдэх шаардлагатай болно
2. Өгөгдлийн сан солигдвол (жишээ нь MongoDB) бүх caller-ыг засах хэрэгтэй
3. Алдааны мэдээлэл хэрэглэгчид шууд харагдаж, аюулгүй байдлын эрсдэл үүсгэнэ

**Засвар:** Домэйн-тусгайлсан алдаа шидэх — `RepositoryError`, `UserNotFoundError` гэх мэт. Доод давхаргын алдааг барьж, өөрийн төрөл рүү хөрвүүлнэ.

## Сайжруулсан API-н товч тайлбар

Сайжруулсан хувилбарыг `partA/src/good/` фолдерт хэрэгжүүлсэн. Гол өөрчлөлтүүд:

- `UserService` interface — нэг үйлдэлд нэг метод
- `User`, `Email`, `UserId` зэрэг branded типүүд
- `UserServiceError` иерархи бүхий өөрийн exception
- `createInMemoryUserService()` factory — concrete класс нуугдсан
- Бүх метод async/Promise-тэй, JSDoc-тай

## Дүгнэлт

Эхний API нь:
- олон үүрэгтэй функц ашигласан
- мэдээллийн далдлалт алдагдсан
- type safety байхгүй
- abstraction зөрчсөн

## Сайжруулснаар:
- нэг үүрэгтэй тодорхой API болсон
- type-safe болсон
- ойлгомжтой, өргөтгөхөд хялбар болсон
- алдааны удирдлага сайжирсан

Ингэснээр API нь илүү найдвартай, тестлэхэд хялбар, хэрэглэгчид ойлгомжтой болсон.
